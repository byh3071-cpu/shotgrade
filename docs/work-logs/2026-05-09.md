## 보안 리뷰: rate limit 우회

### 1차 리뷰 결과

- **High:** 기존 rate limit은 저장된 `shots` row 기준이라 `/api/analyze`만 반복 호출하고 저장하지 않으면 Anthropic 호출 비용을 계속 발생시킬 수 있었음.
- **Medium:** parse 실패 retry가 최대 2회 모델 호출을 만들지만 quota 차감은 saved row 기준이라 비용 방어가 부족했음.
- **Medium:** `saveShotToHistory`가 직접 호출 가능한 Server Action이라 client-provided analysis/promptVersion/base64를 신뢰하는 구조였음.

### Claude Code 수정

- `/api/analyze`에서 모델 호출 전 pending row를 먼저 insert.
- pending row:
  - `image_url = ""`
  - `grade = "P"`
  - `score = null`
  - `analysis = {}`
  - `prompt_version = PROMPT_VERSION`
- 분석 성공 시 같은 row를 `grade`, `score`, `analysis`로 update.
- save action은 이미지 업로드 후 `image_url`만 update.

### 2차 리뷰 결과

- 인증 누락은 보이지 않음.
  - `/api/analyze`: `supabase.auth.getUser()` 확인 후 진행.
  - `saveShotToHistory`: auth 확인 후 upload/update.
  - `updateShotFeedback`: auth 확인 + `.eq("user_id", user.id)`.
- 다른 유저 row 조작 방지는 대체로 유지됨.
  - pending row update와 image update 모두 `id + user_id` 조건 사용.
- **남은 High 리스크:** race condition은 아직 남아 있음.
  - 현재 구조는 `COUNT` 후 `INSERT`라 atomic하지 않음.
  - 동시 요청 N개가 모두 count를 통과하면 `dailyLimit`보다 최대 N-1회 초과 가능.
  - v2에서 Postgres RPC atomic check+insert 또는 quota slot 테이블/constraint/advisory lock으로 해결 예정.
